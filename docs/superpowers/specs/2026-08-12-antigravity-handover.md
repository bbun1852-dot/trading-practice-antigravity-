## 1. 이 프로젝트가 무엇인가

캔들차트 문제를 풀고 **판단 근거까지 채점받는** 기술적 분석 연습 툴입니다.
단순 PnL 계산기가 아닙니다. 존재 이유는 **"내가 놓친 근거가 있는지"** 를 알려주는 것이고,
이 문장이 아래 모든 규칙의 근거입니다.

그래서 **답안지가 되는 신호 집합이 틀리면 제품 전체가 거짓말이 됩니다.** 성능이나
코드 미학보다 "이 태그가 실제로, 정확한 자리에서 나오는가" 가 항상 우선입니다.

### 현재 상태 (2026-08-12 실측)

|---|---|
| 태그 | **105종** (등재 105 == 실측 배출 105, 죽은 태그 0종) |
| 테스트 | 512개 통과 (30 파일) |
| `npm run typecheck` | 통과 |

## 2. 일하는 방식 — 저장소 규칙

서로 방식이 다르니 이 저장소에서 통하는 규칙을 적습니다. **취향이 아니라 계약입니다.**
지난 인계에서 실제로 문제가 됐던 것들이라 하나씩 이유를 붙였습니다.

### 2.1 문서를 믿지 말고 실측하세요

이 저장소는 **문서 수치가 실제와 어긋난 사례가 반복**됐습니다. 설계 문서가 "태그 40종"
이라 적었는데 실제 배출은 48종이었고, "미구현 20종" 이라 적었는데 실제로는 57종이었습니다.

태그 수·발화 빈도·임계값을 다룰 때는 **실데이터로 재고 나서 말하세요.** 캔들은
`.candle-cache/` 에 이미 받아져 있어 네트워크 없이 잽니다:

```ts
import { getCandles } from '../src/data/fileCache'
const END_TIME = Math.floor(Date.UTC(2026, 7, 1) / 1000)  // 창 고정 = 재현 가능
const cs = await getCandles('BTCUSDT', '4h', 1000, END_TIME)
```

임시 측정은 `scripts/_이름.ts` 로 만들어 `npx tsx` 로 돌리고 **끝나면 반드시 지우세요.**
네트워크를 치는 테스트가 `npm test` 에 남으면 안 됩니다.

### 2.2 게이트를 움직이지 마세요 ← 가장 중요

`calibrate.ts` 의 `MEDIAN_MAX`, 발화율 상한 같은 값은 **제품이 무너지는 걸 막는 장치**입니다.
게이트가 막으면 **게이트가 아니라 원인을 고치세요.**

직전 인계에서 실제로 있었던 일입니다. `MEDIAN_MAX` 가 15 → 18 로 올라가 있었는데,
실측해 보니 초과한 계열은 한 개가 1 넘은 것뿐이었습니다. 진짜 원인은 `htf_trend` 가
과다 발화해 혼자 유효 근거의 5.8% 를 먹은 것이었고, 그걸 고치니 **15 에서 10/10 통과**했습니다.
천장을 올렸으면 다음 파트는 더 큰 값에서 같은 일을 했을 겁니다.

게이트를 정말 바꿔야 한다고 판단되면 **커밋을 따로 떼고, 커밋 메시지에 실측 근거를
숫자로 남기세요.** 그러면 검토할 수 있습니다.

### 2.3 인과성이 1번 계약입니다

감지기는 봉 `i` 에서 **봉 `0..i` 만** 보고 판단해야 합니다. 새 감지기에는
`assertNoLookAhead` 테스트가 **반드시** 있어야 합니다.

- `Pivot.barIndex` 는 **확정 시점**(`pivotBar + n`), `pivotBar` 는 실제 봉우리입니다.
  판정에는 `barIndex <= i` 로 거르고, `refs`(사용자가 차트에 그릴 좌표)에는 `pivotBar` 를 쓰세요.
  직전 인계에서 `refs` 가 `barIndex` 를 써서 실제 피벗보다 8봉 뒤를 가리키고 있었습니다.
- **`if (cs.length < 100) return []` 같은 길이 기반 가드는 그 자체가 미래참조입니다.**
  봉 k 의 답이 "k 이후에 봉이 몇 개 더 있는지" 에 달리게 되니까요. 워밍업은 길이가 아니라
  `i` 나 "확정 피벗이 N개 이상" 같은 인과적 조건으로 거세요. 이번에 `assertNoLookAhead` 가
  bar 91 에서 실제로 잡아냈습니다.
- `assertNoLookAhead` 는 신호가 하나도 안 나오면 **스스로 실패**합니다. 공허한 통과는 없습니다.

### 2.4 발화 억제 — 파트마다 반복해서 걸린 함정

**조건이 참인 동안 매 봉 신호를 내면 안 됩니다. 처음 성립한 순간에만 내세요.**

Part 3, Part 4, Part 6 에서 세 번 걸렸습니다. 가장 최근 사례: `htf_trend` 이 1000봉당
91회 발화했고 발화 간격 90개 중 47개가 4봉이었는데 수명이 `recent(8)` 이라 **앞뒤가 항상
겹쳐 한 번 켜지면 꺼지지 않았습니다.** 억제를 넣으니 722 → 126회가 됐습니다.

억제 키에 `i`(현재 봉) 를 넣으면 봉마다 키가 달라져 **억제가 통째로 무효**가 됩니다.
키는 사건이 가리키는 **자리**(예: 뚫린 피벗의 `pivotBar`)로 잡으세요.

상태와 사건을 구별하세요. "추세가 상승이다" 는 상태, "추세가 상승으로 바뀌었다" 는 사건입니다.
**신호는 사건이어야 합니다.**

### 2.5 죽은 태그 0종

`taxonomy.ts` 에 등재됐는데 감지기가 안 내는 태그는 **사용자를 벌주기만 합니다.**
`grader.ts` 는 활성 신호에 없는 체크를 전부 헛다리로 처리하므로, 죽은 태그는 영원히
감점만 되고 맞을 수가 없습니다. 반대로 등재 없이 배출하면 영원히 못 맞히는 유령
⚠️놓침이 됩니다. **taxonomy·감지기·`ruleCheck.ts` 세 곳이 항상 같이 움직여야 합니다.**

"구현했다" 의 정의는 **실데이터에서 실제로 배출된다** 입니다. 등재만 하고 예외 목록에
넣어 초록으로 만들지 마세요 — `taxonomy.test.ts` 의 예외 목록은 **고백이지 편의 도구가
아닙니다.** 실제로 배출되기 시작하면 그 목록이 스스로 실패하도록 짜여 있습니다.

### 2.6 테스트는 실제 불변식을 거세요

이런 건 테스트가 아닙니다. 항상 참이라 아무것도 검증하지 않습니다:

```ts
expect(sigs.length).toBeGreaterThanOrEqual(0)   // ✗
expect(Array.isArray(out)).toBe(true)           // ✗
```

대신 그 변경이 보장하는 성질을 거세요 — "같은 방향이 연달아 나오지 않는다",
"자리마다 한 번만 난다", "SC → AR → ST 순서로 난다", "같은 입력이면 같은 출력".

`synthCandles` 는 **추세가 없는 난수 보행**이라 클라이맥스·강한 추세가 필요한 감지기를
전혀 행사하지 못합니다(실측: 3000봉에서 와이코프 클라이맥스 0회). 그런 감지기는
**도식을 직접 그린 픽스처**로 테스트하세요. `wyckoff.test.ts` 의 `repeatedSchematic` 이 예시입니다.

### ✅ 작업 2 — `detectMSB` 를 BOS 와 CHoCH 로 분리 · 📄 스펙 문서 필요

`src/analysis/smc.ts` 의 `detectMSB` 가 BOS 와 CHoCH 를 구분하지 않습니다. 그래서
**`choch` 가 `msb_*` 와 98% 겹칩니다.** Part 4 에서 발견했지만 Part 1 감지기를 건드려야 해서
미뤘고, 지금은 `choch` 배점을 4 → 2 로 낮춰 **중복 계상만 완화**해 둔 상태입니다.
근본 원인은 그대로입니다.

같은 사건을 두 태그로 세면 채점이 거짓말을 합니다 — 사용자가 하나만 짚어도 "하나 놓쳤다"
가 되고, 둘 다 짚으면 근거 하나로 점수를 두 번 받습니다.

- **BOS**: 추세 **방향으로의** 구조 돌파 (추세 지속)
- **CHoCH**: 추세 **반대 방향의 첫** 돌파 (성격 전환)

추세 방향을 알아야 하므로 직전 구조 상태를 들고 가는 전방 스캔이 자연스럽습니다.
`wyckoff.ts` 의 상태기계가 참고가 됩니다.

- **완료 기준**:
  1. 분리 **전** 겹침률을 실측해 기록 (같은 봉 ±2 안에서 `choch` 와 `msb_*` 가 같이 나는 비율)
  2. 분리 **후** 겹침률 **20% 미만**
  3. `choch` 배점을 원래 값(4)으로 되돌릴 수 있는지 판단하고 근거를 남길 것
  4. calibrate 체크포인트 3개 PASS 유지, 죽은 태그 0종 유지
- **주의**: Part 1 감지기라 영향 범위가 넓습니다. 기존 테스트가 깨지면 **그 테스트가 옳은지
  먼저 판단**하세요. 고쳐야 할 수도, 그 테스트가 맞고 구현이 틀렸을 수도 있습니다.

### ✅ 작업 3 — 진짜 HTF 데이터 계층 · 📄 스펙 문서 필요

`src/analysis/htf.ts` 의 `htf_*` 3종은 **진짜 상위 타임프레임이 아닙니다.** 주어진 봉을
배열 인덱스 0부터 4개씩 묶은 합성입니다. 한계가 둘입니다:

1. 배수가 4 고정이라 1d 차트에서 실재하지 않는 "4일봉" 이 됩니다
2. 캘린더가 아니라 배열 인덱스 기준이라, 데이터 창의 시작이 달라지면 상위 봉 경계도 달라집니다

그래서 세 종 다 B등급(헛다리 감점 절반)입니다 — 사용자가 실제 상위 차트에서 본 것과
다를 수 있다는 고백입니다.

실제 상위 캔들을 받아 쓰도록 바꿔 주세요 (4h → 1d, 1d → 1w).

- **완료 기준**:
  1. `htf_*` 3종이 실제 상위 타임프레임 캔들을 사용
  2. 상위 봉 경계가 **캘린더 기준**이고, 하위 창이 어디서 시작하든 같은 답이 나올 것
  3. `assertNoLookAhead` 통과 — **상위 봉은 닫힌 것만 쓸 것** (안 닫힌 봉으로 판정하면
     같은 자리가 데이터 길이에 따라 다른 답을 냅니다)
  4. B → A 등급으로 올릴 수 있는지 판단하고 **근거를 남길 것** (올릴지 말지는 판단해서
     제안만 하고, 확신이 없으면 B 로 두세요)
  5. calibrate 3개 PASS, 죽은 태그 0종 유지
- **주의**: `Question` 은 지금 봉 배열 하나만 듭니다. 데이터 모델을 바꿔야 하면
  **반드시 스펙 문서를 먼저** 쓰고 시작하세요. 채점 경로(`grader.ts`)가 은닉 구간을
  절대 읽지 않는다는 성질이 테스트로 고정돼 있으니, 상위 봉을 넘길 때 그걸 깨지 마세요.

### ✅ 작업 4 — 죽은 태그 게이트를 자동화

**게이트 7(죽은 태그 0종)이 지금 자동화돼 있지 않습니다.** 직전 작업에서 임시 스크립트로
손으로 쟀습니다. 이건 재발합니다.

`calibrate.ts` 에 체크포인트로 편입해 exit code 로 판정하게 만들어 주세요.

- **완료 기준**:
  1. `npm run calibrate` 가 "등재 태그 수 vs 실측 배출 태그 수" 를 출력하고, 다르면 **exit ≠ 0**
  2. 계열별 발화율 상한(1000봉당 150회)도 같이 판정 — 단, `bar` 수명 태그는 제외
     (`candle_inside_bar`·`ma_aligned_*` 는 매 봉 나지만 수명이 1봉이라 근거를 부풀리지 않습니다)
  3. 기존 체크포인트 3개는 그대로 PASS
- **덤**: `pattern_bull_pennant` 를 재검토해 주세요. 28,000봉에서 0회라 등재 해제한
  상태입니다(근거는 `chartPatterns.ts` 주석). 작업 2·3 이후 데이터가 늘었다면 다시
  나올 수도 있습니다. **나오면 taxonomy·감지기·ruleCheck 세 곳을 같이 되살리세요.**

### ✅ 작업 5 — 오답노트 저장 계층 (헤드리스)

`idb` 의존성이 이미 들어 있는데 쓰이지 않고 있습니다. 문제·답안·채점 결과를 저장하고
다시 꺼내는 계층을 만들어 주세요. **UI 는 만들지 마세요** — 저장·조회 API 까지입니다.

- **완료 기준**:
  1. 저장 → 조회 왕복 테스트 (같은 것이 나오는지)
  2. "틀린 태그" 로 검색 가능 — 오답노트의 핵심은 "내가 자꾸 놓치는 근거가 뭔가" 입니다
  3. 스키마 버전을 들 것. `src/data/fileCache.ts` 의 `CACHE_VERSION` 처리 방식이 참고가 됩니다
     (캐시는 최적화지 진실의 출처가 아니다 — 조금이라도 의심스러우면 버린다)
- **주의**: 브라우저 IndexedDB 는 Node 테스트에서 안 돕니다. 저장 계층을 인터페이스로
  분리해서 테스트에서는 메모리 구현을 끼울 수 있게 하세요.

### ✅ 작업 6 — 34점 패널 연결 (`ruleCheck` 소비자 만들기)

`src/quiz/ruleCheck.ts` 가 **Part 2 부터 소비자 없이 방치**돼 있습니다. 지금 어디서도
호출하지 않습니다(실측 확인).

이건 사장이 직접 정리한 트레이딩 노트의 **34점 가중치 진입 판단 시스템**입니다.
`scripts/drill.ts` 출력에 붙여 주세요.

- **완료 기준**:
  1. `npm run drill` 출력에 34점 패널이 나온다
  2. **채점 점수(100점)와 완전히 분리돼 있다** ← 중요
  3. 34점 패널이 채점 결과를 바꾸지 않는다는 것을 테스트로 고정
- **왜 분리인가**: 34점 체계는 **채점 주체가 아니라 별도 검증 패널**이라고 사장이 결정했습니다.
  그건 "진입할까 말까" 를 판단하는 본인 도구지, 답이 맞았는지 재는 자가 아닙니다.
  이 둘을 섞으면 프로세스 점수가 본인 취향을 품게 됩니다.
