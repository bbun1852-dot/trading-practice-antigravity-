## 1. 요구사항 — 일반론이 아니라 이 저장소의 실측

UI 가 차트에 요구하는 것을 코드에서 뽑았다.

**R1. 캔들 차트 + 재생.** `solverView` 가 은닉 구간을 **데이터에서 잘라서** 준다. 차트에 은닉 봉이 들어갈 일이 없으므로 "마스킹" 기능은 필요 없다 — 채점 후 봉을 하나씩 추가하는 **재생**(실시간 틱과 동일한 시나리오)만 있으면 된다. 어느 라이브러리든 기본기다.

**R2. 프로그램적 오버레이.** 복기 화면에서 정답 근거를 시각화한다. 감지기의 `refs` 구조를 전수 조사하면 그려야 할 도형은 **정확히 4종**이다:

| 도형 | refs 필드 | 쓰는 태그 |
|---|---|---|
| 가격 박스 | `priceHigh~priceLow × fromBar~toBar` | 오더블록·FVG·매물대 |
| 사선 (두 점) | `price@fromBar → price@toBar` | 추세선·채널 |
| 수평 레벨 | `price` | 스윕 레벨·피보·SR |
| 봉 마킹 | `pivotBar` / `barIndex` | 캔들 패턴·와이코프 사건 |

**사용자가 그리는 게 아니라 코드가 그린다.** 태그 선택 UX 결정(2026-08-13)에서 차트 앵커 방식을 탈락시켰으므로 인터랙티브 드로잉 툴은 요구에 없다. 이게 비교의 판을 바꾼다 — 시중 비교글은 대부분 "드로잉 툴" 을 기준으로 하는데 우리는 그게 필요 없다.

**R3. 지표 패널.** momentum 계열 12종의 복기에 RSI/MACD 패널이 필요할 수 있다. 중요한 사실: **지표 값은 이미 우리가 계산한다** (`src/analysis/indicators.ts` — sma·ema·rsi·macd·bollinger·atr·obv). 차트 라이브러리는 그리기만 하면 된다.

**R4. HTF 보조 차트.** `htfCandles` 를 작은 차트로. 메인과 같은 라이브러리면 된다.

**R5. 데이터 규약.** `Candle.time` 은 "UNIX epoch in **SECONDS** (lightweight-charts 규약)" 이라고 타입 정의에 박혀 있다. Part 1 계획서에도 `React·Tailwind·lightweight-charts·zustand 는 Part 2에서` 라고 원안이 적혀 있다.

## 2. 차트 라이브러리

후보를 먼저 거른다. **ECharts** 는 60MB(unpacked)로 금융 특화가 아니고 캔들+금융 오버레이는 곁다리라 탈락. **D3 직접 구현**은 좌표계·줌·스케일을 전부 손으로 만드는 것이라 이 프로젝트 규모에 낭비라 탈락. 남는 실질 후보는 둘이다.

### 2.1 lightweight-charts 5.2.1 (TradingView)

Apache-2.0 · unpacked 3.1MB (gzip ~50KB 수준) · TypeScript 내장

**강점**
- **데이터 규약이 이미 일치한다.** `{ time: epochSeconds, open, high, low, close }` 를 그대로 넣는다. 변환 계층 0.
- **룩앤필이 실전과 같다.** 사장이 실제로 보는 TradingView 차트와 렌더링이 같은 혈통이다. 차트 읽기 연습 도구에서 "연습 화면 ≈ 실전 화면" 은 기능이다.
- 재생(R1)이 가장 기본 시나리오다 — `series.update()` 반복.
- 지표 패널(R3): v5 의 multi-pane 에 line series 로 그린다. **우리 indicators.ts 값을 그대로** 쓴다.
- 생태계·문서·예제가 금융 차트 중 최대. 공식 plugin-examples 에 rectangle 프리미티브 본보기가 있다.

**약점**
- **박스·사선 오버레이가 내장이 아니다.** Series Primitives API 로 캔버스에 직접 그려야 한다. 좌표 변환(`priceToCoordinate`·`timeToCoordinate`)은 라이브러리가 주므로, 도형당 렌더러 ~40줄 × 4종 = **약 200줄 + 테스트**가 우리 부담이다.

**약점의 재평가**: R2 가 "프로그램이 그린다" 이므로 프리미티브가 오히려 정확한 도구다. 한 번 만들면 전부 우리 코드라 "이 근거만 강조/흐림" 같은 복기 인터랙션을 완전히 통제한다. 이 200줄은 어차피 스타일 커스터마이즈로 어디서든 쓰게 될 코드다.

### 2.2 KLineChart 10.0.2

Apache-2.0 · unpacked 2.9MB · TypeScript 내장 · 의존성 0

**강점**
- **`createOverlay` 내장.** segment·rect·피보 등을 `points` 로 프로그램 생성. R2 의 4종을 코드 몇 줄로 해결 — 위의 ~200줄을 아낀다.
- 지표 패널 내장(MACD·RSI 등 수십 종).
- 캔들 특화라 API 표면이 우리 용도와 가깝다.

**약점**
- **시간 규약 불일치.** KLC 는 timestamp(ms). 우리 모델(seconds)과 어긋나 ×1000 변환이 데이터 흐름 전면에 깔린다. 사소해 보이지만 이 저장소가 가장 경계하는 종류의 상시 실수 유발원이다.
- **내장 지표가 자기가 계산한다.** 우리 감지기가 본 RSI 와 차트 패널의 RSI 가 기간·시드 차이로 미묘하게 다를 수 있다. "감지기는 다이버전스라는데 패널에는 안 보인다" 는 채점 신뢰를 깎는 최악의 사용자 경험이다. 물론 커스텀 지표로 우리 값을 주입할 수 있지만, 그러면 "내장이라 편하다" 는 강점이 상쇄된다.
- **v9 → v10 대개편 직후.** 웹에 v9/v10 문서가 혼재하고 마이그레이션 이슈가 진행형이다. 내장 오버레이 스타일을 우리 톤에 맞추는 override 작업도 결국 필요해서, "공짜 오버레이" 는 절반만 공짜다.
- 커뮤니티가 중국어 중심 — 영문 자료·사례가 LWC 대비 얇다.

### 2.3 판정표

| 기준 (가중치는 요구 빈도 순) | LWC 5 | KLC 10 |
|---|---|---|
| R5 데이터 규약 일치 | **그대로** | ×1000 변환 상시 |
| R2 오버레이 4종 | 자체 구현 ~200줄 | 내장 (스타일 override 별도) |
| R3 지표 = 감지기 값 일치 | **우리 값 그대로 그림** | 내장은 자체 계산 (불일치 위험) |
| R1 재생 | 기본기 | 기본기 |
| 실전(TradingView) 룩 | **동일 혈통** | 다름 |
| API 안정성 | v5 성숙 | v10 대개편 직후 |
| 문서·생태계 | 최대 | 보통 (중문 중심) |
| 라이선스·크기 | Apache-2.0 · 3.1MB | Apache-2.0 · 2.9MB |

**권고: lightweight-charts.** KLC 가 이기는 항목은 "오버레이 200줄 절약" 하나인데, 그 대가로 시간 규약 변환·지표 이중 계산·v10 안정성 리스크 셋을 산다. 우리 요구가 인터랙티브 드로잉이었다면 답이 뒤집혔을 것이다 — 그게 없어서 LWC 다.

**KLC 를 골라야 하는 시나리오** (반대 근거의 정직한 기록): 이후에 "사용자가 차트에 직접 추세선을 그려 답하는" 모드를 추가하기로 결정한다면, 드로잉 툴 자작은 비용이 커서 KLC(또는 LWC + 드로잉 플러그인) 재검토가 맞다. 현재 UX 결정은 그 모드를 배제했다.

## 3. 프레임워크

UI 의 실제 규모부터: 화면 2~3개(문제 풀이 / 복기 / 오답노트), 라우팅 사실상 불필요, 전역 상태는 `Question`·`Answer`·`GradeReport`·재생 tick 정도. 차트는 어느 프레임워크에서든 ref 로 imperative 하게 다룬다 — 프레임워크의 차이는 **시트(체크박스 78~105개 + 실시간 예상 감점)와 리포트** 렌더링에서만 난다.

| | React 19 | Svelte 5 | Vanilla TS |
|---|---|---|---|
| 저장소 관성 | **Part 1 계획서의 원안** | 없음 | 없음 |
| 시트/리포트 반응형 UI | 충분 | 충분·더 가벼움 | 손 배선 (낭비) |
| 협업(Antigravity 포함) 친숙도 | 최고 | 미지수 | — |
| 차트 통합 예제 | 최다 | 적음 | — |
| 번들 | ~50KB | ~10KB | 0 |

**권고: React 19.** Svelte 가 기술적으로 열등해서가 아니다 — 계획서가 React 를 전제했고, 바꿀 근거가 "더 가볍다" 뿐이라면 그건 요청에 없는 개선이다. Vanilla 는 체크박스 105개의 상태·파생값(예상 감점) 배선을 손으로 하는 순간 절약이 아니라 낭비가 된다.

**상태 관리 — zustand 권고.** 재생 애니메이션의 tick 을 차트 컴포넌트(imperative)와 진행 표시 UI 가 동시에 구독해야 하는데, Context 로 하면 tick 마다 트리 리렌더가 난다. zustand 는 구독 지점만 갱신되고 실질 ~1KB 다. 다만 이건 스펙 단계에서 뒤집어도 싼 결정이라 여기서 확정하지 않는다.

**스타일 — Tailwind 는 보류.** 원안에 있었지만 화면 2~3개에 빌드 체인을 늘릴 가치가 있는지 스펙에서 판단한다. 이것도 싼 결정이다.

## 4. 리스크와 스파이크 계획

권고안의 최대 리스크는 하나다: **프리미티브 4종을 우리가 만들 수 있는가.** 말로 검증하지 않고 스파이크로 검증한다.

**스파이크 (UI 파트 Task 1, ~반나절)**
1. Vite + React + LWC 로 BTCUSDT 4h 400봉 캔들 렌더
2. 가격 박스 프리미티브 1종 구현 — 실제 `detectOrderBlocks` 의 refs 로 오더블록을 그린다
3. `solverView` → 재생(`series.update` 로 은닉 봉 순차 추가) 동작 확인
4. **게이트: 셋 다 되면 진행. 프리미티브에서 막히면 이 문서로 돌아와 KLC 로 전환한다** — 전환 비용이 가장 싼 시점이 이때다.

스파이크가 통과하면 UI 파트 스펙(화면 흐름·컴포넌트 경계·태그 시트 UI)을 쓰고 시작한다. 태그 시트의 금지사항 5개는 `2026-08-13-tag-selection-ux-decision.md` 가 이미 못 박았다.
